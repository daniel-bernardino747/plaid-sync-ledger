# RCA-001: Sync cursor advanced without the transactions it covered

| | |
| --- | --- |
| Status | Resolved |
| Severity | SEV-2: silent data loss in user ledgers, no outage |
| Type | **Simulated incident.** The defect was introduced on purpose to exercise detection and recovery. The reproduction is real: [`rca-001-repro.patch`](rca-001-repro.patch) applied to `packages/core/src/sync.ts`, run with `pnpm chaos kill-mid-commit`. All numbers below come from that run. |
| Affected component | `syncItem()` in `packages/core/src/sync.ts` (the transactions sync worker) |

## Summary

A change wrote the sync cursor in its own statement, before the transaction
that stores the transactions it covers. A worker killed between the two
writes left a cursor pointing past data that was never stored, so the retry
never fetched it again. 85% of transactions went missing with no error.

Times up to detection are approximate, relative to the start of the
reproduction run, and read from its process log. The rows before T+0 and after
detection are part of the simulation.

## Impact

- 3 of 3 Items affected in the reproduction.
- 686 of 807 expected live transactions missing (85%). Each Item kept between
  21 and 58 of its 269 transactions.
- No error, retry, dead job or log warning was produced. Every sync job ended
  `succeeded`, and each Item's stored cursor matched Plaid's latest cursor.
  From the system's own point of view everything was healthy.
- No data was exposed. The loss was recoverable because Plaid still holds the
  full history (see Correction).

## Root cause

**Direct cause.** The cursor and the records it covers were written in two
separate database transactions:

```ts
// defective
await db.$executeRaw`UPDATE items SET cursor = ${finalCursor} WHERE ...`; // commit #1
return db.$transaction(async (tx) => { /* apply added/modified/removed */ }); // commit #2
```

A cursor is a promise that "everything before this point is stored". Committing
it before the records breaks that promise for any crash between commit #1 and
the end of commit #2.

**Why it was silent.** `/transactions/sync` is a delta feed. Once the stored
cursor moves forward, the skipped changes are never offered again. There is no
error to catch: the next call is a valid request that correctly answers "nothing
new". Our own health signals (job status, cursor equals Plaid's head) are all
derived from the cursor, so they agreed with the bad state.

**Why it got past tests.** Without a crash, the two-commit version produces
exactly the right ledger. The `clean` chaos scenario and every happy-path test
passed. Only a test that kills the process **between** the two writes can tell
the versions apart.

**The rule this broke.** A checkpoint (cursor, offset, watermark) must be
committed atomically with the work it acknowledges. On a delta feed, writing
the checkpoint first turns any crash into silent data loss.

## Correction

1. **Code.** The cursor is written in the same Postgres transaction as the
   records, as the first statement of that transaction, guarded by a
   compare-and-set on the starting cursor (ADR 0003, ADR 0004):

   ```ts
   return db.$transaction(async (tx) => {
     const fenced = await tx.$executeRaw`
       UPDATE items SET cursor = ${finalCursor}
        WHERE id = ${itemId} AND cursor IS NOT DISTINCT FROM ${c0}`;
     if (fenced !== 1) return { outcome: "cursor_moved" };
     await applyPages(tx, ...);
   });
   ```

   A crash at any point now rolls back the cursor together with the records.

2. **Data repair for affected Items.** Reset their cursor and sync from the
   beginning:

   ```sql
   UPDATE items SET cursor = NULL WHERE id = ANY($affected);
   INSERT INTO sync_jobs (item_id, kind) SELECT unnest($affected), 'transactions_sync'
   ON CONFLICT (item_id, kind) WHERE status = 'queued' DO NOTHING;
   ```

   This is safe because applying `/transactions/sync` pages is idempotent:
   upserts are keyed on Plaid's `transaction_id`, and removals are soft deletes.
   The test `is idempotent: replaying the same update from the same cursor
   changes nothing` (`packages/core/test/sync.test.ts`) replays a full history
   over an existing ledger and asserts an identical hash.
